# M Nithya Shree Portfolio

A full-stack portfolio website for an AI & Data Science engineering student focusing on cloud, Linux, networking, cybersecurity, and data analytics.

## Stack

- Frontend: React, Vite, TypeScript, custom responsive CSS, React Router, Framer Motion, Lucide React
- Backend: Node.js, Express.js, MongoDB, Mongoose, JWT
- Dev tools: Git, GitHub, Postman, ESLint, Prettier

## Features

- Responsive portfolio pages and smooth navigation
- Project and certification detail pages
- Contact form with validation and backend storage
- Admin authentication and dashboard for content management
- Public photo gallery with admin-managed JPG, PNG, and WebP uploads persisted in MongoDB GridFS
- MongoDB-backed API and seed data
- Dark/light theme and motion-aware accessibility

## Local setup

1. Copy `.env.example` to `.env` and update values if needed.
   - Set a strong `JWT_SECRET`.
   - Set `ADMIN_EMAIL` and `ADMIN_PASSWORD` for the initial admin account. The password is hashed before MongoDB storage.
2. Install dependencies from the project root:
   - `npm install`
   - `npm install --prefix client`
   - `npm install --prefix server`
3. Start the full stack from the project root:
   - `npm run dev`
4. Frontend runs at `http://localhost:5173`
5. Backend runs at `http://localhost:5000`

The API requires `MONGODB_URI` and will not connect to local MongoDB or start with in-memory fallback data. For local development, configure the same MongoDB Atlas connection string used by your deployed API.

## Deploy publicly on Render

`render.yaml` configures one Render Node web service to build the Vite client and serve both the portfolio and Express API from the same public URL. Contact messages, portfolio data, resumes, and gallery photos persist in MongoDB Atlas (GridFS for binary files); a separate upload disk is not needed.

1. Push this repository to GitHub.
2. In Render, choose **New + → Blueprint**, connect this repository, and apply the `render.yaml` Blueprint.
3. When prompted for unsynced values, enter your Atlas `MONGODB_URI`, admin email/password, contact inbox, and SMTP sender settings. The blueprint sets `MONGODB_DATABASE=portfolio` to use your existing database.
4. In MongoDB Atlas, give the configured database user `readWrite` access to that database and allow the Render service to connect under Network Access.
5. For Gmail notifications, create a Google App Password and set it as `SMTP_PASSWORD` in Render. Never use your regular Google password.
6. Wait for `/api/v1/health` to pass, then open the Render service URL and test the contact form, admin login, and resume uploads/downloads.

Render supplies the public site origin and service port. The frontend calls `/api/v1` on the same origin; the API automatically allows the Render origin. `JWT_SECRET` is generated by the Blueprint. Private credentials stay in Render's environment settings, not in Vite variables.

The split Vercel-static/Render-API setup remains possible using [vercel.json](vercel.json), but the single-service Render setup avoids separate frontend/API origin configuration.

The app creates its MongoDB collections automatically on first writes: `admins`, `projects`, `certifications`, `skills`, `experiences`, `achievements`, `messages`, and `profiles`. Resume binaries are stored by GridFS in `resumes.files` and `resumes.chunks`; the profile document stores each GridFS file ID. MongoDB calls these collections, not tables, and you do not need to create them manually. Set `MONGODB_DATABASE` to your existing database name to connect this deployment to your portfolio data. If a host's DNS resolver refuses Atlas SRV queries, optionally set `MONGODB_DNS_SERVERS=8.8.8.8,1.1.1.1`, provided that host permits external DNS.

Do not commit `.env` or put secrets in `VITE_*` variables. Vite variables are public in the built frontend. The committed `.env.example` contains placeholders only; configure real values in the hosting dashboards.

### Admin email and contact notifications

Set `ADMIN_EMAIL` to the Google address you want to use for admin sign-in and `ADMIN_PASSWORD` to a new strong admin password. On server startup, that configured account is created or updated in MongoDB; log in with the configured email. Contact form submissions are saved in MongoDB first, then emailed to `CONTACT_EMAIL` (which defaults to `ADMIN_EMAIL`). Messages stay in MongoDB when marked read or archived; these actions update the stored status rather than deleting the message.

Configure SMTP on the API host and in the local `.env` for local testing. Never put `SMTP_PASSWORD` in the frontend or a `VITE_*` variable.

For Gmail, the code defaults to `SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=465`, and `SMTP_SECURE=true`. `SMTP_USER`, `SMTP_FROM`, and `CONTACT_EMAIL` default to `ADMIN_EMAIL`, so the only required local mail setting is `SMTP_PASSWORD`. Generate a Google App Password with 2-Step Verification enabled, then put that App Password in the blank `SMTP_PASSWORD` line in your local `.env`; do not use your regular Google password. Set the same secret as `SMTP_PASSWORD` in the API host's environment settings for production.

For Outlook.com, use `SMTP_HOST=smtp-mail.outlook.com`, `SMTP_PORT=587`, and `SMTP_SECURE=false` (STARTTLS). Set `SMTP_USER` and `SMTP_FROM` to the Outlook account. Use an app password if required by your account's MFA/security settings, and ensure SMTP AUTH is enabled for the mailbox.

After configuring mail, restart the backend and submit a test from the portfolio contact page. The form confirms whether it only saved the message or also sent the email notification. The admin Messages tab shows each message's email-delivery status and lets you retry failed notifications. Failed email delivery never discards the MongoDB message.

## Project structure

- `client/` - Vite React frontend
- `server/` - Express API and MongoDB models
- `README.md` - project overview

## Scripts

- `npm run dev` - starts the frontend and backend together
- `npm run build` - builds the frontend for production
- `npm run server` - runs the backend in dev mode
- `npm run client` - runs the frontend in dev mode
- `npm run start` - runs the backend production server
- `npm test` - validates the project model exports

## Admin access

- Login: `http://localhost:5173/admin/login`
- Dashboard: `http://localhost:5173/admin/dashboard`
- Public portfolio: `http://localhost:5173/`

The backend sets an HTTP-only authentication cookie and also returns a bearer token for compatibility with the current client. MongoDB Atlas is required for the API to start; the server does not switch to local or in-memory storage.
